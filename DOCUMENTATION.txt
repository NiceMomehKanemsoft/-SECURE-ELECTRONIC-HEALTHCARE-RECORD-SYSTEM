SYSTEM OVERVIEW
---------------
SECURE-ELECTRONIC-HEALTHCARE-RECORD-SYSTEM The Secure Electronic Healthcare Record System (EHRS) is a web-based application, It allows healthcare staff to securely store, access, and manage patient medical records. All clinical data is encrypted and access is strictly controlled based on user roles.

The system is designed with security as the top priority:
- All medical records are encrypted using AES-256-GCM
- Passwords are hashed using Argon2id
- Every login requires a 6-digit MFA code (Google Authenticator)
- Every action is recorded in a tamper-proof audit log
- Each role can only access the record types relevant to their job

================================================================================
HOW THE SYSTEM WORKS - STEP BY STEP
================================================================================

------------------------------------------------------------------------
STEP 1: AUTHENTICATION (All Users)
------------------------------------------------------------------------

When a user visits the login page:

  a) They enter their username and password.
  b) The system checks the password against the Argon2id hash in the database.
  c) If correct, the user is moved to the MFA verification page.
  d) The user opens Google Authenticator and enters the 6-digit TOTP code.
  e) The system verifies the code using RFC 6238 (30-second window).
  f) If the code is correct, a secure session is created with:
       - user_id
       - username
       - role
       - mfa_verified = true
       - session_token (random 32-byte hex, used for encryption key derivation)
  g) The user is redirected to their role-specific dashboard.

Security during login:
  - After 5 failed attempts, the account is locked for 15 minutes
  - Session ID is regenerated after successful MFA to prevent session fixation
  - Sessions expire after 30 minutes of inactivity


------------------------------------------------------------------------
STEP 2: PATIENT REGISTRATION (Doctor)
------------------------------------------------------------------------

Only doctors can register new patients.

  a) Doctor logs in and goes to Patients > Register
  b) Fills in patient details:
       - First name, Last name
       - Date of birth
       - Gender
       - Phone number
       - Email address
       - Address
       - Blood type
  c) The system generates a unique UUID for the patient (e.g. a3f2c1d4-...)
  d) Patient is saved to the database
  e) The action is recorded in the audit log

The patient UUID is used later as part of the encryption key derivation
for all records belonging to that patient.


------------------------------------------------------------------------
STEP 3: CREATING A MEDICAL RECORD (Doctor / Nurse / Lab Tech)
------------------------------------------------------------------------

When a user creates a medical record:

  a) They navigate to a patient's profile
  b) Click "Add Record" and select the record type
     (only types allowed for their role are shown)
  c) They fill in the clinical content (e.g. diagnosis notes, prescription details)
  d) On submission, the system encrypts the content:

     ENCRYPTION PROCESS:
     -------------------
     i.   A random 96-bit IV (Initialization Vector) is generated
     ii.  A random 128-bit salt is generated
     iii. A 256-bit encryption key is derived using PBKDF2-SHA256:
            Key = PBKDF2(session_token + "|" + patient_uuid, salt, 100000 iterations)
     iv.  The content is encrypted using AES-256-GCM with the derived key
     v.   The key is immediately zeroed from memory after use
     vi.  Stored in the database: ciphertext, IV, auth_tag, salt, key_id, access_roles

     IMPORTANT: The encryption key is NEVER stored anywhere.
     It is re-derived on demand from the user's session token and patient UUID.

  e) The access_roles JSON field records which roles can decrypt this record
  f) The action is logged in the audit trail


------------------------------------------------------------------------
STEP 4: VIEWING / DECRYPTING A MEDICAL RECORD
------------------------------------------------------------------------

When a user views a patient's records:

  a) The system fetches all records for that patient from the database
  b) For each record, it checks if the user's role is in the access_roles field
  c) If the role is NOT allowed, the record is shown as [ENCRYPTED - ACCESS DENIED]
  d) If the role IS allowed, the system decrypts the record:

     DECRYPTION PROCESS:
     -------------------
     i.   The IV, auth_tag, salt, and ciphertext are retrieved from the database
     ii.  The key is re-derived: PBKDF2(session_token + "|" + patient_uuid, salt)
     iii. AES-256-GCM decryption is performed
     iv.  The GCM authentication tag is verified automatically
          (if tampered, decryption fails and an error is shown)
     v.   The key is zeroed from memory
     vi.  The plaintext content is displayed to the user

  e) The view action is recorded in the audit log


------------------------------------------------------------------------
STEP 5: AUDIT LOGGING (Automatic)
------------------------------------------------------------------------

Every action in the system is automatically logged. Users cannot disable this.

Each audit log entry contains:
  - User ID and username
  - SHA-256 hash of the patient UUID (for privacy)
  - Operation type (e.g. LOGIN, CREATE_RECORD, VIEW_RECORD, LOGIN_FAILED)
  - Status (success / failure / warning)
  - IP address
  - Browser/device info
  - Timestamp
  - Chain hash (SHA-256 of previous entry + current data)

The chain hash links every log entry to the previous one, like a blockchain.
If any log entry is modified or deleted, the chain breaks and the system
detects tampering automatically.

Database triggers also prevent UPDATE and DELETE on the audit_logs table,
making the log truly append-only.

ROLE-BY-ROLE USER GUIDE

------------------------------------------------------------------------
DOCTOR (dr.smith)
------------------------------------------------------------------------

Dashboard shows:
  - Total patients
  - Recent records
  - Quick action buttons

What a Doctor can do:

  PATIENTS:
  - Register new patients (Patients > Register)
  - Search patients by name or ID (Patients > Search)
  - View full patient profile and history (Patients > List > click patient)
  - Edit patient details (Patients > Edit)

  MEDICAL RECORDS:
  - Create any record type:
      * Diagnosis       - clinical diagnosis notes
      * Prescription    - medication and dosage
      * Lab Result      - test results
      * Psychiatric     - mental health notes
      * Vital Signs     - blood pressure, temperature, pulse, etc.
  - View and decrypt ALL record types for any patient
  - View lab file uploads

  AUDIT:
  - View audit logs for their own actions

  Typical Doctor workflow:
  1. Log in with username + password + MFA code
  2. Go to Patients > Register to add a new patient
  3. Open the patient profile
  4. Click Add Record > Diagnosis > fill in notes > Save
  5. Click Add Record > Prescription > fill in medication > Save
  6. Later, open the patient and click View on any record to decrypt and read it
  7. Log out when done

  2. Search for a patient by name
  3. Open the patient profile
  4. Click Add Record > Vital Signs > fill in readings > Save

  - All other record types show as ACCESS DENIED

  Typical Lab Tech workflow:
  1. Log in with username + password + MFA code
  2. Go to Records > Lab Upload

  4. Upload the lab result file and enter result details

ADMINISTRATOR (admin)
------------------------------------------------------------------------

Dashboard shows:
  - Total users
  - System health status
  - Recent audit activity

What an Admin can do:

  USER MANAGEMENT (Admin > Users):
  - View all user accounts
  - Create new user accounts (Admin > Create User)
  - Edit user details and roles (Admin > Edit User)
  - Deactivate user accounts (Admin > Deactivate User)
  - Cannot create accounts with admin role for security

  AUDIT LOGS (Audit > Logs):
  - View the full audit trail of all system activity
  - Filter logs by user, operation, date, status
  - Export audit logs (Audit > Export)
  - View individual log entry details (Audit > View Detail)

  SYSTEM HEALTH (Admin > System Health):
  - Check database connection status
  - View audit chain integrity status
  - Monitor active sessions

  WHAT ADMIN CANNOT DO:
  - Admin CANNOT view, open, or decrypt any clinical records
  - Admin CANNOT see patient medical content
  - This is enforced both by role checks and by cryptographic access control
    (the access_roles field on every record never includes 'admin')

  Typical Admin workflow:
  1. Log in with username + password + MFA code
  2. Go to Admin > Users to check all accounts are active
  3. Go to Audit > Logs to review recent system activity
  4. Go to Admin > System Health to verify system is running correctly
  5. If a new staff member joins, go to Admin > Create User to add them
  6. Log out when done

SECURITY FEATURES SUMMARY
================================================================================

  FEATURE                   DETAIL
  ------------------------------------------------------------------------
  Password Hashing          Argon2id (memory=64MB, time=4, threads=1)
  MFA                       TOTP RFC 6238, 6-digit, 30-second window
  Encryption                AES-256-GCM per record
  Key Derivation            PBKDF2-SHA256, 100,000 iterations, 128-bit salt
  Key Storage               Keys are NEVER stored, derived on demand only
  Session Security          HttpOnly cookies, SameSite=Strict, 30min timeout
  Session Fixation          Session ID regenerated after MFA success
  CSRF Protection           Synchronizer token on all POST forms
  Rate Limiting             5 failed logins = 15 minute lockout
  Audit Trail               SHA-256 chained, append-only, trigger-protected
  Role Enforcement          PHP role checks + JSON access_roles per record
  Input Sanitization        htmlspecialchars on all output, PDO prepared statements
  Directory Protection      .htaccess blocks direct access to config/crypto/database
  Security Headers          X-Frame-Options, X-Content-Type-Options, CSP, etc.

================================================================================
ENCRYPTION TECHNICAL DETAIL
================================================================================

Key Derivation:
  key = PBKDF2-SHA256(
            password  = session_token + "|" + patient_uuid,
            salt      = random 128-bit value (stored per record),
            iterations = 100,000,
            keylen    = 32 bytes (256 bits)
        )

Encryption:
  iv         = random 96 bits (generated fresh per record)
  ciphertext = AES-256-GCM-Encrypt(plaintext, key, iv)
  auth_tag   = 128-bit GCM authentication tag (stored separately)

Stored in database per record:
  - ciphertext  (base64 encoded)
  - iv          (binary 12 bytes)
  - auth_tag    (binary 16 bytes)
  - kdf_salt    (binary 16 bytes)
  - key_id      (random non-secret identifier)
  - access_roles (JSON array of permitted roles)

The encryption key is derived fresh on every decrypt request and
immediately zeroed from memory after use. It is never written to
disk, database, or logs.


================================================================================
AUDIT CHAIN INTEGRITY
================================================================================

Each audit log entry has a chain_hash calculated as:

  chain_hash = SHA-256(
      previous_chain_hash +
      user_id +
      operation +
      status +
      timestamp
  )

The first entry uses a chain of 64 zeros as the previous hash.

To verify integrity, the system recalculates every chain hash from
the beginning and compares it to the stored value. If any entry has
been modified, deleted, or inserted out of order, the chain breaks
and the system shows the tamper_detected.php page.

Database triggers additionally block any UPDATE or DELETE on the
audit_logs table at the database level.


================================================================================
SESSION SECURITY
================================================================================

After successful MFA verification, the session contains:

  $_SESSION['user_id']       - Database user ID
  $_SESSION['username']      - Username string
  $_SESSION['role']          - Role (doctor/nurse/lab_tech/admin)
  $_SESSION['mfa_verified']  - true
  $_SESSION['last_activity'] - Unix timestamp (for timeout check)
  $_SESSION['session_token'] - Random 32-byte hex (used in key derivation)

Session rules:
  - Cookie is HttpOnly (not accessible by JavaScript)
  - Cookie is SameSite=Strict (blocks CSRF via cross-site requests)
  - Session expires after 30 minutes of inactivity
  - Session ID is regenerated after MFA to prevent session fixation
  - On logout, session is fully destroyed
